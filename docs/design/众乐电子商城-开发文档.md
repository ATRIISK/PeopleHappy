## 1. 项目概述

众乐电子商城是一个轻量级 B2C 电商平台，包含用户端（商品浏览/购物车/下单/支付宝沙箱扫码支付）和管理后台（商品/订单/用户管理）。项目采用 Java Spring Boot 3 + Vue 3 全栈开发，对接支付宝开放平台沙箱环境（个人开发者无需企业资质，接口/签名机制与生产环境一致，可平滑切换），引入 Redis 和 RabbitMQ 做性能优化与异步处理。

**目标：** 做一个能写简历的完整电商项目，展示产品思维和技术深度。

## 4. 数据库设计（8 张表）

> 表结构已通过 MySQL 客户端创建完毕 ✅
> ⚠️ user 表已有注册数据；product 和 category 表需手动执行 `resources/db/init-data.sql` 初始化

### 4.1 用户表 `user`

```sql
CREATE TABLE `user` (
    `id`          BIGINT       NOT NULL AUTO_INCREMENT,
    `username`    VARCHAR(50)  NOT NULL UNIQUE,
    `password`    VARCHAR(255) NOT NULL COMMENT 'BCrypt 加密',
    `phone`       VARCHAR(20),
    `avatar`      VARCHAR(255),
    `role`        VARCHAR(20)  NOT NULL DEFAULT 'USER' COMMENT 'USER / ADMIN',
    `update_time` DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    `is_deleted`  TINYINT DEFAULT 0 COMMENT '逻辑删除: 0-未删除 1-已删除',
    `create_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`)
);
```

### 4.2 分类表 `category`

```sql
CREATE TABLE `category` (
    `id`          BIGINT      NOT NULL AUTO_INCREMENT,
    `name`        VARCHAR(50) NOT NULL,
    `parent_id`   BIGINT      DEFAULT NULL COMMENT '父分类ID，0=一级分类',
    `level`       TINYINT     DEFAULT 1 COMMENT '层级：1=一级 2=二级',
    `sort`        INT         DEFAULT 0 COMMENT '排序序号',
    `create_time` DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `update_time` DATETIME,
    `is_deleted`  TINYINT     DEFAULT 0,
    PRIMARY KEY (`id`)
);
```

### 4.3 商品表 `product`

```sql
CREATE TABLE `product` (
    `id`             BIGINT         NOT NULL AUTO_INCREMENT,
    `name`           VARCHAR(200)   NOT NULL,
    `description`    TEXT,
    `price`          DECIMAL(10,2)  NOT NULL COMMENT '现价',
    `original_price` DECIMAL(10,2)  COMMENT '原价（划线价）',
    `image`          VARCHAR(255)   COMMENT '商品主图',
    `images`         TEXT           COMMENT '多图 JSON 数组 ["url1","url2"]',
    `category_id`    BIGINT         NOT NULL,
    `category_name`  VARCHAR(50)    COMMENT '分类名称（冗余字段）',
    `sales`          INT            NOT NULL DEFAULT 0,
    `stock`          INT            NOT NULL DEFAULT 0,
    `rating`         DOUBLE         DEFAULT 0 COMMENT '评分 0-5',
    `status`         TINYINT        NOT NULL DEFAULT 0 COMMENT '0上架 1下架',
    `create_time`    DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `update_time`    DATETIME,
    `is_deleted`     TINYINT        DEFAULT 0,
    PRIMARY KEY (`id`),
    KEY `idx_category` (`category_id`),
    KEY `idx_status` (`status`)
);
```

### 4.4 购物车表 `cart`

```sql
CREATE TABLE `cart` (
    `id`         BIGINT NOT NULL AUTO_INCREMENT,
    `user_id`    BIGINT NOT NULL,
    `product_id` BIGINT NOT NULL,
    `quantity`   INT    NOT NULL DEFAULT 1,
    `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_user_product` (`user_id`, `product_id`)
);
```

### 4.5 订单表 `order`

```sql
CREATE TABLE `order` (
    `id`             BIGINT       NOT NULL AUTO_INCREMENT,
    `order_no`       VARCHAR(32)  NOT NULL UNIQUE COMMENT '订单号（yyyyMMddHHmmss+4位随机数，共18位）',
    `user_id`        BIGINT       NOT NULL,
    `total_amount`   DECIMAL(10,2) NOT NULL,
    `status`         TINYINT      NOT NULL DEFAULT 0 COMMENT '0待支付 1已支付 2已发货 3已完成 4已取消 5已退款',
    `address_id`     BIGINT,
    `transaction_id` VARCHAR(64)  COMMENT '支付宝交易号（trade_no）',
    `prepay_id`      VARCHAR(64)  COMMENT '预支付ID（当前扫码支付流程未使用，支付宝 precreate 接口只返回 qr_code，保留字段以便扩展）',
    `pay_time`       DATETIME,
    `create_time`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    KEY `idx_user` (`user_id`),
    KEY `idx_order_no` (`order_no`),
    KEY `idx_status` (`status`)
);
```

### 4.6 订单项表 `order_item`

```sql
CREATE TABLE `order_item` (

    `quantity`   INT            NOT NULL,
    `price`      DECIMAL(10,2)  NOT NULL COMMENT '下单时价格快照',

    KEY `idx_order` (`order_id`)
);
```

### 4.7 收货地址表 `address`

```sql
CREATE TABLE `address` (

    `name`        VARCHAR(50)  NOT NULL COMMENT '收件人',
    `phone`       VARCHAR(20)  NOT NULL,
    `province`    VARCHAR(50)  NOT NULL,
    `city`        VARCHAR(50)  NOT NULL,
    `district`    VARCHAR(50),
    `detail`      VARCHAR(200) NOT NULL,
    `is_default`  TINYINT      DEFAULT 0,
    PRIMARY KEY (`id`),

```

### 4.8 支付流水表 `payment_log`

```sql
CREATE TABLE `payment_log` (
    `id`             BIGINT       NOT NULL AUTO_INCREMENT,
    `order_no`       VARCHAR(32)  NOT NULL,
    `transaction_id` VARCHAR(64),
    `pay_type`       VARCHAR(16)  COMMENT 'PRECREATE（支付宝扫码支付）',
    `total_fee`      INT          COMMENT '金额单位：分',
    `trade_state`    VARCHAR(32)  COMMENT 'WAIT_BUYER_PAY/TRADE_SUCCESS/TRADE_FINISHED/TRADE_CLOSED',
    `notify_raw`     TEXT         COMMENT '支付宝异步通知原始报文',
    `create_time`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    KEY `idx_order_no` (`order_no`)
```

### 7.4 订单超时取消流程 ✅ 已实现（RabbitMQ 死信队列 DLX）

**方案：原生 TTL + 死信交换机（DLX）实现延迟队列**，不依赖 rabbitmq_delayed_message_exchange 插件。

**消息流向：**
```
Producer → order.exchange → order.delay.ttl.queue（TTL=30min）
  → 消息过期 → 死信投递到 order.cancel.exchange → order.cancel.queue
  → OrderTimeoutConsumer 消费 → cancelOrderByTimeout()
```

**流程：**
1. `createOrder()` 订单创建成功后，末尾通过 RabbitTemplate 发送延迟消息（消息体 = 订单ID），用 try-catch 包裹，**MQ 发送失败不影响下单主流程**（打日志告警，后续可定时任务补偿）
2. 消息进入 `order.delay.ttl.queue`（`x-message-ttl`=30分钟，`x-dead-letter-exchange`→`order.cancel.exchange`，`x-dead-letter-routing-key`→`order.cancel`）
3. 30 分钟内用户付了款 → 消息过期后消费者检查到 status≠0 → 跳过，不重复取消
4. 30 分钟还没付款 → 消息过期 → 死信队列 `order.cancel.queue` → `OrderTimeoutConsumer.handleOrderTimeout()` 收到订单ID
5. `OrderService.cancelOrderByTimeout(orderId)`：
   - 查订单（系统自动操作，无需校验 userId）
   - ★ 条件更新 `cancelPendingOrder`（`UPDATE ... SET status=4 WHERE id=? AND status=0`）
     - 影响行数=0 → 订单已支付/已取消 → 直接 return（**不会误取消已支付订单**）
     - 影响行数=1 → 取消成功 → 再 `restoreStockByOrderId()` 恢复库存（先改状态再恢复，防并发双倍恢复）
6. 前端倒计时：OrderDetail.vue（待付款订单显示「剩余支付时间」）+ Pay.vue 均基于 `订单创建时间 + 30 分钟` 计算剩余时间，与后端 TTL 完全对齐

**⚠️ 队列名说明：**
- 延迟队列用 `order.delay.ttl.queue`，**不是** `order.delay.queue`
- RabbitMQ 的队列参数（x-message-ttl / x-dead-letter-*）创建后不可修改；若本机之前跑过旧版应用，`order.delay.queue` 已以"无参数"形式存在，再声明会报 406 PRECONDITION_FAILED 或参数被忽略 → 超时取消永远不触发
- 换新名后 RabbitMQ 会以带 TTL/死信参数的配置重建队列（旧队列残留无害，可手动删除）

**相关文件：**
- `application.yml` — RabbitMQ 连接参数：`connection-timeout: 200`（建立连接超时 200ms，快速失败触发自动重连，默认 5 秒间隔重试）、`requested-heartbeat: 60s`（心跳保活，防止空闲连接被判定为死连接）
- `RabbitMQConfig.java` — 交换机 / 延迟队列 / 死信队列声明（`ORDER_TIMEOUT_MS = 30 * 60 * 1000`）
- `OrderTimeoutConsumer.java` — `@RabbitListener` 监听 order.cancel.queue
- `OrderServiceImpl.createOrder()` — 发延迟消息；`cancelOrderByTimeout()` — 超时取消 + 恢复库存
- `OrderMapper.cancelPendingOrder()` — 条件更新（status 0 → 4，防并发）

## 8. Redis 缓存设计 ✅ 已实现（2026-08-12 阶段二 + 2026-08-13 code-review 两轮修复）

缓存全部在 Service 层实现，Controller 不感知。

| 场景 | 数据结构 | Key（实际） | TTL | 策略 | 状态 |
|---|---|---|---|---|---|
| 商品详情 | String | `product:detail::1`（Spring Cache 格式 = 缓存名::key） | 30 min | 读时回填（@Cacheable）；写时清除（@CacheEvict：下单扣库存/取消退单恢复库存时清对应商品） | ✅ |
| 热门商品榜 | ZSet | `product:hot` | 1 h | 定时刷新（@Scheduled 每小时）+ 读取时缓存为空自动回填；member=商品ID、score=销量 | ✅ |
| 分类树 | String | `category:tree::tree` | 1 h | 读时回填（@Cacheable） | ✅ |
| 购物车 | Hash | `cart:{userId}` | - | ⚠️ 当前使用 MySQL 存储（已跑通全流程），Redis 优化推迟到后续迭代 | ⏳ 推迟 |

**实现说明（对齐代码）：**

- **商品详情**：`ProductServiceImpl.getProductById()` 加 `@Cacheable(cacheNames = "product:detail", key = "#id")`
  - 用方法参数 id 做 key，实际 Redis key 是 `product:detail::1`；TTL 走 CacheManager 默认配置 30min
- **分类树**：`CategoryServiceImpl.getCategoryTree()` 加 `@Cacheable(cacheNames = "category:tree", key = "'tree'")`
  - CacheManager 对 `category:tree` 缓存名单独覆盖 TTL 1h
  - 指定 `key = "'tree'"` 的原因：方法无参时 Spring Cache 默认用 `SimpleKey []` 做 key，会生成难看的 `category:tree::SimpleKey []`，指定常量 key 后变成干净的 `category:tree::tree`
- **热门榜**：`ProductServiceImpl` 手写 `StringRedisTemplate.opsForZSet()`（ZSet 不是 Spring Cache 抽象原生支持的结构，不能用 @Cacheable）
  - 读取：`reverseRange("product:hot", 0, 7)` 按 score 降序取前 8 个商品ID → `selectBatchIds` 批量查库 → 按榜单顺序组装 VO（Map 索引保序）；**命中缓存但过滤下架/已删除商品后不足 8 个时，回退数据库查全量 Top8 并刷新缓存**（code-review 修复，避免首页"热门推荐"显示 4 个甚至 0 个）
  - 缓存空 → 读取时顺手回填（不用干等整点）；Redis 故障 → try-catch 降级回数据库（首页不挂）
  - 定时刷新：`@Scheduled(cron = "0 0 * * * ?")` 每小时整点 → **不删 key，逐个 ZADD 覆盖更新 score + `removeRange`（ZREMRANGEBYRANK）清理掉出前 8 的旧成员** → `expire 1h` 双保险（code-review 修复：原来先 delete 再 ZADD 有毫秒级空窗，并发读见空 ZSet 会误判缓存为空、重复查库惊群）
  - 为什么用 StringRedisTemplate（code-review 修复已删除 RedisConfig 里无调用方的自定义 RedisTemplate Bean）：ZSet 的 member 存商品ID，JSON 序列化器对数字的反序列化有歧义（Long 读回可能是 Integer），String 模板类型干净零歧义；StringRedisTemplate 是 Spring Boot 自动配置，无需声明
- **序列化**：CacheManager 与 RedisTemplate 统一用 Jackson JSON 序列化（`RedisConfig.buildJsonSerializer()`），Redis 里存可读 JSON 文本（带 @class 类型信息，反序列化还原 Java 类型），ARDM 可视化工具可直接查看
- **缓存一致性（code-review 修复 2026-08-13，经典延时双删）**：下单扣库存 / 取消·退单·超时恢复库存都会改 `product.stock`，而商品详情有 30 分钟缓存 → 用户会看到旧库存（"详情页有库存，下单却提示库存不足"）。`OrderServiceImpl` 在扣/恢复库存后调 `productService.clearProductDetailCache(productId)`，缓存操作封装在 ProductService 层，订单模块不直接操作 Redis（符合 §8 缓存全部在 Service 层）。该方法实现**经典延时双删**：
  - **第一次删除**：`@CacheEvict` 注解（方法正常返回后自动删 `product:detail::{id}`，key 与 `@Cacheable` 的 `#id` 值一致）
  - **第二次删除**：**绑定在事务提交之后**（`TransactionSynchronization.afterCommit` 回调），事务提交成功后再延时 500ms 由守护线程池（`ScheduledExecutorService`，线程名 `cache-delay-delete`）删一次同一 key
  - **为什么必须延时双删**：第一次删除发生在订单事务提交**之前**，存在并发窗口——删除后、事务提交前，并发读请求可能读到旧库存并回填缓存（删了又回填旧值，残留最多 30 分钟）。第二次延时删除能把被回填的旧值清掉，保证缓存最终一致
  - **为什么第二次删除要等事务提交**：若从调用时刻算 500ms，而订单事务因 RabbitMQ 发送重试（`spring.rabbitmq.template.retry` 3 次、初始间隔 1s，最坏拖 ~3s）迟迟不提交，第二次删除会在事务提交**前**执行——之后并发读照样回填旧值，窗口没闭上。所以必须等事务真正提交后再延时删（code-review 修复）
  - **为什么延时 500ms**：经验值，覆盖"读缓存 miss → 查库 → 回填"的耗时。为什么用线程池不用 `Thread.sleep`：不能阻塞下单请求线程
  - **实测**：下单后 `product:detail::1` 立即被删（第一次），日志（线程 `cache-delay-delete`）确认事务提交后 500ms 第二次删除执行
- **Redis 故障降级（code-review 修复 2026-08-13）**：`RedisConfig` 提供 `CacheErrorHandler`（`CachingConfigurer.errorHandler()`），缓存读写失败打日志 + 不抛异常 → `@Cacheable` 方法体照常查库返回。Redis 挂了商品详情/分类树自动降级（不再 500），热门榜本来就是手写 try-catch 降级。实测：停掉 Redis 后三个接口仍返回 200
- **@CacheEvict 预留**：管理后台改商品/分类时，在保存方法上加 `@CacheEvict(cacheNames = "product:detail", allEntries = true)` / `@CacheEvict(cacheNames = "category:tree", allEntries = true)`
- **购物车**：维持 MySQL 存储，Redis Hash 方案后续迭代

## 10. 代码规范（MVC 红线）

| 层 | 可以做 ✅ | 不可以做 ❌ |
|---|---|---|
| **Controller** | 接收参数、@Valid 校验、调 Service、包装 Result | 写业务判断、直接调 Mapper、操作 HttpSession |
| **Service** | 业务逻辑、事务（@Transactional）、缓存、调 Mapper、Entity↔VO 转换 | 返回 Entity 给 Controller、处理 HttpServletRequest、SQL 拼接 |
| **Mapper** | SQL 查询、MyBatis-Plus 条件构造 | 业务逻辑判断 |
| **Entity** | 映射表结构，仅字段+注解 | 包含业务方法、直接返回前端 |
| **VO** | 定义前端需要的字段 | 包含敏感字段（密码） |

## 12. 支付宝沙箱支付配置说明 ✅ 后端已实现，使用前需自行配置密钥

因个人开发者无法申请微信支付企业商户号，改用**支付宝开放平台沙箱环境**验证完整支付链路：
无需任何企业资质，免费开通，接口名/签名算法(RSA2)/SDK 和生产环境完全一致，仅网关地址、沙箱专用 APPID 不同，未来可平滑切换到生产环境。

开发时需准备：
1. **支付宝开放平台账号**，进入「沙箱环境」页面获取沙箱 APPID
2. **RSA2 密钥对**：用官方「RSA签名验签工具2.0」生成商户应用私钥 + 商户公钥（PKCS8 格式），把商户公钥填入沙箱后台，换回**支付宝公钥**
3. **支付宝沙箱钱包 App**（不是普通支付宝App，普通App扫不了沙箱二维码）
4. **内网穿透（隧道）**：支付宝回调需要你的后端有一个公网可达的地址。本地开发时可选：
   - **localhost.run**（推荐，零配置）：`ssh -R 80:localhost:8074 nokey@localhost.run` → 获得 `https://xxxx.lhr.life` 地址
   - **ngrok**（需注册）：`ngrok http 8074` → 获得 `https://xxxx.ngrok.io` 地址
   - 把生成的公网地址填入 `notify-url` 中（如 `https://xxxx.lhr.life/api/pay/notify`）<br>⚠️ 每次重启隧道地址会变化，需同步更新 `application.yml` 并重启后端

配置在 `application.yml` 中（以下为配置项说明，**真实密钥值见 application.yml，文档不展示密钥**）：

```yaml
alipay:
  app-id: 沙箱APPID（在支付宝开放平台-沙箱环境页面获取）
  private-key: 商户应用私钥（用"RSA签名验签工具2.0"生成密钥对，PKCS8 格式）
  alipay-public-key: 支付宝公钥（生成密钥对后，把商户公钥填入沙箱后台，沙箱会返回这个）
  gateway-url: https://openapi-sandbox.dl.alipaydev.com/gateway.do   # 新版沙箱网关（旧版 openapi.alipaydev.com 已废弃），生产环境是 openapi.alipay.com
  notify-url: https://0654527ccb32ad.lhr.life/api/pay/notify   # 本地开发隧道地址，目前用 localhost.run，每次重启需更新
  sign-type: RSA2
  charset: UTF-8
  format: json
```

⚠️ 当前 `application.yml` 内嵌的是**支付宝沙箱环境密钥**（沙箱无真实资金，仅开发调试用，风险可控）。沙箱私钥提交仓库可接受，但**生产环境严禁把私钥写进配置文件**，必须改用环境变量（如 `SPRING_ALIPAY_PRIVATE_KEY`）或配置中心注入，且不得提交到仓库。
