## 记忆层与索引机制优化分析（只读诊断，方案待确认）

参考 Anthropic《Effective context engineering for AI agents》四类模式（compaction / structured note-taking / sub-agent / just-in-time retrieval）+ Context Academy 四 pattern（just-in-time、server-side compaction、prompt caching、memory tool）作为基准，审计了项目两套记忆子系统。

### 新发现的关键缺陷（此前 22 轮审计均未记录）

1. **关键词召回恒 0 命中（最严重）**：`KnowledgeBaseService.hybridSearch` 把**完整用户问句**当 keyword 传给 `ProductMapper.findForKnowledgeBase`，SQL 是 `name LIKE CONCAT('%',#{keyword},'%') OR description LIKE ...`。商品名/描述不可能包含整句 → keyword-top-k=5 形同虚设，"混合检索"实际只有向量路生效。
2. **saveIndex() 全量重写 4.2MB**：每次商品 upsert/remove 都同步 `vectorStore.save()` 序列化写 200×1536 维浮点。索引文件 4,224,244 字节（实测）。
3. **向量语义同质，召回无区分度**：200 个演示商品 description 完全相同（"批量生成的演示商品，用于测试..."），仅名称编号/分类不同 → 一商品一文档（无分片）+ 无 MMR 多样性控制 → 召回结果对用户无意义。
4. **无会话记忆导致多轮指代失效**：`AiConfig.chatClient` 明确不配 memory（为防游客串上下文），每轮无状态。"这个多少钱""有没有便宜的"这类指代/省略 query 向量路也拿不到语义。
5. **metadata 快照过期 + 无对账**：向量 text 内嵌旧价格/描述（buildIndex 有意不对账，code-review F7 取舍），商品改价后向量语义仍是旧值。
6. **融合策略实为"关键词优先"假设计**：LinkedHashSet 插入顺序决定排序，无 similarity score 参与排序/阈值过滤。
7. **上下文固定注入**：context-top-n=5 × doc-max-chars=500 ≈ 3500 token 恒定；且 `[n] 《name》 价格 ¥x` 与 text 内"价格: ¥x" 字面重复。
8. **文件记忆层膨胀且无淘汰**：Claude memory 15 文件 104,829 字节；document-code-sync-audit.md 32KB(31%) + project-progress.md 14KB；MEMORY.md 索引是纯链接无分类/摘要/时效。"Spring Boot 3.5.14" 出现于 5 个文件，完成度 ✅ 68 次重复。project-sync-complete.md(第1-7轮) 已被 document-code-sync-audit(第9-22轮) 覆盖但两者并存于索引。
9. **记忆层矛盾未消解实证**：project-progress.md 仍写"乐观锁"，与第 23 轮纠偏结论矛盾——即上一轮梳理中已记录的那处滞后。

### 关键取舍与风险（本次分析新增结论）
1. **连接池配置实际不生效**：`spring.data.redis.lettuce.pool.*` 只在引入 `commons-pool2` 且 Lettuce 池化开启时才生效；当前 pom 无显式 `commons-pool2`，**这四项配置是死配置**。默认 Lettuce 是共享单连接（线程安全），并发够用但高并发下会串行化。改进：显式加 `commons-pool2` 依赖。
2. **无密码明文**：`application.yml` 未配 password，本地 Redis 无认证；生产必须走环境变量。
3. **缓存穿透无防护**：`getProductById` 对不存在的 id 也会 `@Cacheable` 缓存 null 值吗？—— 取决于是否 `unless = "#result == null"`，**当前未加 unless**，理论上穿透会被缓存住（好事）；但恶意刷随机 id 仍会反复查库。`getCategoryTree` 无参数不涉及。
4. **击穿**：热门榜有"补齐逻辑"（命中但过滤下架后不足 8 个 → 回退查库刷新）算部分缓解；商品详情**无互斥锁重建**，高并发下同一过期瞬间可能多线程同时查库回填（当前 30min TTL + 数据量小，影响有限）。
5. **雪崩**：TTL 固定 30min/1h，无随机抖动——同一批商品若同时过期会有瞬时压力。建议加 `±10%` 随机 TTL。
6. **序列化兼容性**：`LaissezFaireSubTypeValidator`（信任所有子类型）+ `activateDefaultTyping` 组合，**反序列化存在反序列化 Gadget 风险**；且 VO 字段增删会导致老缓存 JSON 反序列化失败（当前 TTL 30min 内自愈，可接受）。
7. **延时双删固有 trade-off**：第二次盲删可能删掉刚被并发读回填的**新**正确缓存（记忆台账已记，不改）。
8. **分类树无失效入口**：`category:tree` 1h TTL，但后台**没有分类管理功能**，只能等 TTL 自然过期——当前安全，若将来加分类管理必须补 `@CacheEvict`。
9. **热门榜 ZSet 残留**：下架商品在整点刷新前仍在 ZSet 里，靠读取时 `eq(status,0)` 过滤 + 补齐逻辑兜住。
