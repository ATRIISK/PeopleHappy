## 面试专题：RabbitMQ 死信 + 关单消息完整流转（已核代码）

- 死信触发条件（RabbitMQ 通用三种）：① 消息被 reject/nack 且不重回队列 ② 队列超长（x-max-length）③ 消息 TTL 过期。**本项目只用了第 ③ 种**：`order.delay.ttl.queue` 设 `x-message-ttl=1800000` + `x-dead-letter-exchange=order.cancel.exchange`，且该队列无消费者，消息只能等 TTL 到期变死信 → DLX 转发到 `order.cancel.queue` 被消费。即"延迟 = 死信"实现，不依赖 delayed_message_exchange 插件。
- 完整链路：createOrder 事务内（步骤9，try-catch 包裹，MQ 挂不影响下单）convertAndSend(order.exchange, order.delay, orderId) → TTL 队列停 30 分钟 → 过期死信 → order.cancel.exchange → order.cancel.queue → OrderTimeoutConsumer.handleOrderTimeout → cancelOrderByTimeout：selectById → 条件更新 `UPDATE ... SET status=4 WHERE id=? AND status=0`（影响行数0=已支付→跳过，防竞态）→ restoreStockByOrderId 恢复库存+清商品详情缓存。
- 消费者 catch 异常不抛出，防 auto 模式下消息无限重回队列死循环；打日志人工介入。
- 面试细节点：队列参数创建后不可变（曾因旧队列无参数导致 406 PRECONDITION_FAILED / 超时永不触发，故改名 order.delay.ttl.queue）；TTL 配在队列级而非消息级，避免队头阻塞（队头消息 TTL 长会挡住后面短 TTL 的消息）；已支付订单的消息照样过期成死信，靠消费者查状态幂等跳过。

## 面试专题：下单扣库存并发能力评估（已核代码）

- 结论：现有方案（单行原子条件更新）**正确性满分、并发能力中等**。不同商品=不同行锁，互不影响（横向扩展 OK）；**同一热点商品=全局串行**（纵向瓶颈）。
- 瓶颈定量：updateStock 在事务第 7 步，后面还有插订单项、删购物车、查 VO、发 MQ——**行锁持有时间=整个事务**，单热点商品吞吐约几百 TPS（理论估算，项目无压测数据）。
- 优化路径三级：① 扣库存挪到事务最后/拆小事务（改动最小）② Redis Lua 预减（10w+ QPS）③ MQ 异步落库削峰（需补偿：Redis 扣了 MQ 丢了要对账回滚）。
- 面试叙事：商城选 DB 行锁是"流量没到、简单可靠、同步反馈体验好"的正确取舍；抢票系统选 Redis Lua+MQ 是秒杀量级的必然——同一问题两种量级两种答案。仍未做 JMeter 压测，若补上"0 超卖+P99"数据可让卖点从理论变实证。
